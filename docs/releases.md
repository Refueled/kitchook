# Releases and compatibility

KitchooK! source and builder releases use [semantic versioning](https://semver.org/). The initial distribution release is `0.1.0`.

## What a release contains

Pushing a signed-off `v<package-version>` tag runs the GitHub-hosted release workflow. It verifies the tag/version match, runs the test suite and example build, publishes the `linux/amd64` and `linux/arm64` OCI builder manifest to `ghcr.io/refueled/kitchook`, and creates GitHub source release notes with the immutable image digest and source revision.

Consumers pin the release version and image digest in their private instance repository. Recipe updates do not require an application release. Application upgrades are deliberate pin changes followed by a rebuild and normal static-host rollback procedure.

## Compatibility policy

- Recipe Markdown remains canonical and independent of KitchooK! versions.
- The supported input/configuration and output contracts are documented in [contracts.md](contracts.md).
- The static recipe JSON export is additive: consumers must ignore fields they do not recognize.
- Breaking recipe-schema, instance-configuration, builder-interface, or static-output changes require an explicit migration and a semantic-major-version decision.
- Builder images include OCI source revision/version labels and SLSA-style build provenance generated by GitHub Actions.

## Preparing a release

1. Update `package.json` and `package-lock.json` to the chosen semantic version.
2. Run `npm test` and `npm run build` from a clean locked install (`npm ci --ignore-scripts`).
3. Review dependencies, lockfile, base-image tag/digest, Dockerfile, and builder test results.
4. Create and push the matching `v<version>` tag.
5. Confirm the GitHub release's source revision, image manifest digest, provenance attestation, and both platform manifests before changing an instance pin.

The tag workflow is intentionally the only publication path. Pull requests and ordinary branch pushes do not receive registry credentials or publish images.
